Тестовое задание: end-to-end LLM-as-judge для code-RAG

Роль: Middle ML Engineer
Срок (ориентир): 3–5 рабочих дней
Доступ к нашему репозиторию и исходникам CondorService: не требуется и не предоставляется.

1. Контекст: наш проект (кратко)

Мы развиваем code-RAG по крупной C++/Win32 (MFC) кодовой базе Windows-сервиса. Пользователь задаёт вопрос на RU/EN; система:

  1. Retrieval — гибрид BM25 + dense (FAISS, BGE), fusion, MMR, расширение по эвристическому call graph.
  2. Сбор контекста — чанки (функции, switch-блоки, классы) с лимитом по символам.
  3. Генерация — несколько вызовов одной и той же базовой LLM (draft → refine → verifier при противоречии контексту).
  4. API — OpenAI-compatible POST /v1/chat/completions (подключение OpenWebUI и др.).

Сейчас регрессия — детерминированный eval: ключевые слова, файлы в evidence, forbidden terms, флаг should_have_answer (формат JSONL, поля вроде reference_answer для людей, не для автоматического семантического сравнения). Это дёшево и стабильно в CI, но не измеряет семантическую корректность, галлюцинации и качество формулировки.

Цель тестового: спроектировать и реализовать end-to-end прогон с LLM-as-judge на той же модели, что и генератор, и выдать набор классических метрик на расширенном eval-наборе — чтобы при смене промпта, retrieval или модели мы видели: стало лучше или хуже.

4. Схема eval-набора (JSONL)

Один объект на строку. Обязательные поля:

{
  "id": "wm_en_01_diff_engine",
  "question": "Which class or module performs the core text diff in WinMerge?",
  "language": "en",
  "should_have_answer": true,
  "reference_answer": "Short gold answer in 1–3 sentences with concrete symbols from the repo.",
  "required_evidence_any": ["path/to/file.cpp"],
  "tags": ["diff", "architecture"]
}

Рекомендуемые поля (для судьи и отладки):

Поле Назначение
reference_answer Эталон для метрики correctness (судья сравнивает смысл, не побайтовое совпадение).
required_evidence_any Ожидаемые файлы в retrieval evidence (для context_recall-подобной метрики).
forbidden_claims_any Фразы, которых не должно быть в ответе (галлюцинации).
should_have_answer false — корректный ответ: отказ / «нет в контексте», без выдуманных фактов.
difficulty easy | medium | hard (для разбивки в отчёте).

Минимум 30 кейсов: ≥ 24 с should_have_answer: true, ≥ 6 негативных.

5. LLM-as-judge (требования)

5.1. Модель

  • Тот же endpoint и та же model_name, что и у RAG under test (один MODEL_URL + MODEL_NAME в .env).
  • Температура судьи: 0.
  • Судья не должен видеть reference_answer при оценке faithfulness (только question + retrieved context + candidate answer).
  • Для correctness судья может видеть reference_answer (reference-based LLM judge — стандартная практика).

5.2. Структура вызова судьи (минимум два промпта)

  1. Correctness (0–1 или 1–5 → нормализовать в [0, 1]):
    «Насколько ответ по смыслу соответствует эталону, учитывая вопрос?»

  2. Faithfulness (0–1):
    «Есть ли утверждения в ответе, которые не поддержаны приведённым контекстом retrieval?»

Опционально (бонус): Relevance (0–1) — ответ по теме вопроса.

Ответ судьи — строго JSON, например:

{
  "score": 0.85,
  "label": "mostly_correct",
  "reason": "One sentence justification."
}

5.3. End-to-end

На каждый кейс:

question → answer_fn(question) → { answer, context, evidence_files }
         → judge_correctness(question, answer, reference_answer)
         → judge_faithfulness(question, answer, context)
         → case metrics

context — тот текст, который реально ушёл в промпт генератора (не весь репозиторий).

6. Метрики (обязательный минимум)

Агрегировать по всему датасету и (желательно) по language / difficulty.

Метрика Определение
pass_rate Доля кейсов, где correctness ≥ τ (τ = 0.7, зафиксировать в README).
mean_correctness Среднее correctness [0, 1].
mean_faithfulness Среднее faithfulness [0, 1].
hallucination_rate Доля кейсов с faithfulness < 0.5 при should_have_answer: true.
false_refusal_rate Доля кейсов с should_have_answer: true, где ответ — отказ/«нет данных», а correctness < 0.3.
false_answer_rate Доля кейсов с should_have_answer: false, где correctness ≥ 0.5 (модель уверенно соврала).
evidence_recall Доля кейсов, где хотя бы один файл из required_evidence_any попал в evidence_files (если поле задано).
composite_score Взвешенная сумма: 0.45·mean_correctness + 0.35·mean_faithfulness + 0.20·evidence_recall (веса можно обосновать в README).

Сравнение «лучше / хуже»: два прогона (baseline vs improved) → таблица Δ по всем метрикам; exit code 1, если composite_score упал более чем на ε = 0.02 (опционально в CLI).

8. Критерии приёмки

  • Воспроизводимый README: с нуля до отчёта ≤ 30 минут на машине с GPU/доступом к вашему LLM endpoint.
  • ≥ 30 кейсов по WinMerge, эталоны правдоподобны (выборочно проверим 5 кейсов по GitHub).
  • Судья на той же модели, что генератор; faithfulness без подсказки эталона.
  • Все метрики из §6 в EvalMetrics + per-case dump.
  • Демонстрация двух прогонов (например, top_k=3 vs top_k=10 или слабый vs сильный промпт) с таблицей Δ.
  • Код: типы, без хардкода секретов, .env.example.

Бонус (не обязательно): subset с двойным судьёй + agreement; калибровка порога τ по 5 ручным разметкам; экспорт в CSV для Grafana.
